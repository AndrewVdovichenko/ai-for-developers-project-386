# Хранилище календаря: факты для решения #10

Исследование [#13](https://github.com/AndrewVdovichenko/ai-for-developers-project-386/issues/13), 18 ноября 2026. Контекст: один сервер Fastify / Node.js 26 / TypeScript 7, одновременные HTTP-запросы, отдельный сервис БД допустим. Это доказательства для обсуждения, а не выбор БД или готовая схема.

## Следствия для атомарного бронирования

Следующее — предлагаемые конструкции на основе гарантий выше; они требуют реализации и конкурентных тестов.

- Выбор, замена и подтверждение Бронирования слота должны включать проверку доступности, изменение занятости и сохранение результата операции в одну транзакцию. При неудачной замене rollback оставляет прежнее Бронирование слота. Успешный commit, после которого потерян HTTP-ответ, восстанавливается по сохранённому ключу операции.
- В PostgreSQL возможны Serializable с повтором всей операции либо блокировка существующей общей строки календаря перед проверкой/изменением на Read Committed. `SELECT FOR UPDATE` только найденных пересечений недостаточен, когда выборка пуста. Отдельный exclusion constraint на едином наборе занятых интервалов усиливает защиту. [Блокировки](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [изоляция](https://www.postgresql.org/docs/current/transaction-iso.html).
- В SQLite путь — короткая `BEGIN IMMEDIATE`-транзакция с проверкой пересечений до записи. Нельзя выпускать подключение или выполнять сетевой запрос посреди операции. `busy_timeout` ограничивает ожидание, но не отменяет необходимость обработки ошибки. [Транзакции](https://www.sqlite.org/lang_transaction.html), [busy_timeout](https://www.sqlite.org/pragma.html#pragma_busy_timeout).
- Уникальный ключ операции и сравнение отпечатка запроса отделяют повтор от повторного использования ключа с другими данными. Проверку и результат хранить атомарно с доменным изменением. Уникальность гарантирует БД; совпадение payload и политика срока хранения — логика приложения. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS), [SQLite CREATE TABLE](https://www.sqlite.org/lang_createtable.html#unique_constraints).
- Истечение срока нельзя выразить постоянно корректным индексным условием «expires_at > now()»: время меняется без записи строки. Предлагается явно исключать просроченные Hold при проверке и переводить их из активной занятости в той же транзакции. Позднее подтверждение повторно проверяет свободный интервал. Схема должна учитывать совместно Hold и Booking, иначе независимые таблицы не защитят друг от друга. Это проектное следствие требований карты, не свойство конкретного драйвера.

## Моменты и местное Расписание

Предложение: начала, окончания и сроки Hold хранить как UTC-моменты: PostgreSQL `timestamptz`, SQLite INTEGER с явно заданными миллисекундами Unix. На границе HTTP — однозначный формат с `Z`. Проверять `start < end`, использовать полуоткрытые интервалы. Недельное Расписание хранить отдельно: день недели + местное начало/окончание (минуты от полуночи либо `time without time zone`) + IANA-имя Часового пояса календаря. Фиксированное UTC-смещение не заменяет пояс с сезонными правилами; преобразовывать конкретную дату по правилам согласованного решения #5. Это рекомендация модели, основанная на [семантике типов PostgreSQL и часовых поясов](https://www.postgresql.org/docs/current/datatype-datetime.html) и [представлениях SQLite](https://www.sqlite.org/datatype3.html#date_and_time_datatype).

Удобно выразить PostgreSQL-специфичные ограничения; соответствие строк SQL и TS-модели проверяется отдельно. | Kysely поверх драйвера | Типизированные имена таблиц/колонок и результаты, транзакционный API, диалекты PostgreSQL и SQLite. Типы не доказывают совпадение реально развёрнутой схемы и не заменяют блокировки/ограничения. Для специфичного SQL остаётся `sql`. Схему типов нужно сопровождать или генерировать. [Kysely](https://kysely.dev/), [транзакции](https://kysely.dev/docs/examples/transactions/simple-transaction), [генерация типов](https://kysely.dev/docs/generating-types) |

Для SQLite отдельно выбирается драйвер. В Node.js 26.13.1 встроенный `node:sqlite` предоставляет синхронный `Database` (`DatabaseSync` — устаревший алиас): его методы блокируют вызывающий поток. Worker уменьшает влияние на HTTP-цикл, но не увеличивает число одновременных писателей. [Node.js SQLite](https://nodejs.org/api/sqlite.html). Совместимость выбранных версий `pg` / Kysely / SQLite-драйвера с TS 7 здесь не проверялась запуском; это проверка реализации, не установленный факт.

## Миграции, постоянный том и тесты

Рекомендация: версионированные SQL-миграции, журнал применённых версий и отдельная команда `db:migrate` до запуска API; один исполнитель миграций с блокировкой, ошибка останавливает развёртывание. Не использовать автосинхронизацию схемы при каждом HTTP-старте. Kysely умеет выполнять миграции и сериализовать конкурирующие запуски; его файлы миграций по умолчанию TS с `up`/`down`, поэтому для требования именно `.sql` нужен адаптер либо отдельный runner. Старые миграции не должны зависеть от текущих TS-моделей. [Kysely migrations](https://kysely.dev/docs/migrations).

Docker volume живёт вне жизненного цикла контейнера. PostgreSQL требует постоянного каталога данных сервиса БД; SQLite — постоянного каталога с файлом БД, WAL и сопутствующими файлами, не только одного файла. Сохранённый volume не является резервной копией и может быть явно удалён. [Docker volumes](https://docs.docker.com/engine/storage/volumes/), [SQLite WAL](https://www.sqlite.org/wal.html#the_wal_file). Перезапуск приложения и потеря питания — разные условия: в SQLite WAL + `synchronous=NORMAL` возможна потеря последних commit при сбое питания; для более сильной durability рассматривается FULL. [synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous). Для PostgreSQL не отключать гарантии WAL/fsync ради скорости без отдельного решения. [Надёжность](https://www.postgresql.org/docs/current/wal-reliability.html).

Рекомендация тестовой изоляции: тот же движок, что выбран для production; PostgreSQL — отдельная временная БД на worker/прогон, SQLite — отдельный временный каталог на worker. Схема создаётся теми же миграциями. HTTP-тесты используют реальные отдельные подключения; внешний rollback тестового клиента не откатит commit серверного клиента ([привязка транзакции к client](https://node-postgres.com/features/transactions)). SQLite `:memory:` полезен для узких тестов, но не проверяет файловый WAL/перезапуск ([in-memory](https://www.sqlite.org/inmemorydb.html)). Обязательные сценарии будущей реализации: два одновременных пересекающихся выбора; неудачная замена сохраняет прежний Hold; гонка подтверждения и истечения; повтор ключа после потерянного ответа; перезапуск между commit и ответом; изоляция разных тестовых workers.

## Что остаётся решить человеку

SQLite уменьшает число сервисов при цене одного писателя; PostgreSQL добавляет сервис и предоставляет независимую защиту пересечения диапазонов. Без нагрузки/целевой задержки нельзя доказать, что ограничение SQLite станет узким местом. Выбор движка, драйвера/query builder и конкретной стратегии сериализации остаётся за обсуждением #10. Исследование не включает нагрузочный эксперимент или проверку приложения.
